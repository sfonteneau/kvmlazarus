# MeshKVM v9 - P1 / P2 / P3

Base exacte : `kvmlazarus-main.zip` fourni par l'utilisateur. Le protocole
reste `meshkvm7`. Sources de developpement, pas un binaire Windows qualifie.

## P1 - reception, decodage et presentation separes

Ancien chemin : callback reseau -> timer GUI -> JPEG -> import TBitmap par
rectangle -> Canvas.Draw -> marqueur B -> ACK.

Nouveau chemin : callback reseau -> FIFO bornee -> TKvmVideoWorker ->
composition CPU BGRX32 -> publication d'un etat coherent -> ACK. Le timer GUI
prend le dernier etat complet disponible et le presente independamment.

- `client/kvm_video_worker.pas` possede ses decodeurs. Il n'utilise ni TBitmap,
  ni TCanvas, ni Synchronize, ni Queue vers le thread graphique.
- `DecodeIntoSurface` ecrit le JPEG directement a sa position dans le tampon
  CPU BGRX32. Plus de BMP intermediaire ou bitmap temporaire pour chaque tuile.
- Le repli JPEG est FCL (FPReadJPEG/TFPMemoryImage), lui aussi hors de la GUI.
  H.264 est egalement decode par ce worker lorsqu'il est integre/disponible.
- Le thread graphique reste seul proprietaire des objets LCL. Sous Windows,
  `kvm_present_win.pas` dessine le DIB BGRX via StretchDIBits, sans import LCL
  par rectangle. Sous les autres widgetsets : un import par presentation.
- `MESHKVM_RAW_IMAGE=0` force le chemin d'import LCL sous Windows, utile pour
  comparer le rendu natif. Cela ne reactive pas le decodage sur le thread GUI.

La boite de presentation conserve seulement le dernier etat coherent. Remplacer
une presentation non peinte ne perd PAS une tuile : tous les deltas acceptes
ont d'abord ete appliques a l'image CPU de reference. Les tampons publies ne sont
plus modifies ; les ecritures suivantes utilisent une copie sur ecriture.

## P2 - ACK de composition et envoi des rectangles deja disponibles

Le ACK signifie "lot decode et compose dans l'etat CPU", PAS "image peinte".
Il ne part ni a la simple reception reseau ni apres un JPEG refuse. Un echec
produit un NACK et attend un nouveau S ; aucune image partielle de ce lot n'est
publiee. Les D (generation/disponibilite du bureau) et I (reception de saisie)
sont conserves dans une file ordonnee, sans coalescence.

`server/kvm_server.pas` separe la cadence de capture de l'envoi du cache.
Un ACK reveille le thread avec un evenement : les rectangles encore en cache
peuvent partir sans attendre une autre capture/encodage ni le prochain tick FPS.
`shared/kvm_schedule.pas` calcule le prochain delai a partir du debut du cycle,
pas en ajoutant une periode complete au temps de travail deja consomme.

**Le serveur garde UN lot en vol par client**, les numerotations, les versions
par tuile, les NACK et les limites de transport. Ce n'est pas un pipeline reseau
multi-lots sans borne. Sur une liaison a fort RTT, cette limite reste une
contrainte ; cette passe cible d'abord les blocages inutiles en LAN et dans LCL.

Bornes : 128 paquets / 16 Mio comprimes dans la file du worker, 128 evenements
UI ordonnes, ecran <=16 777 216 pixels et <=8192 par axe. Les surfaces brutes
peuvent chacune atteindre 64 Mio ; plusieurs references/buffers CPU et les
allocations LCL/decodeurs coexistent. Les 16 Mio ne sont PAS une limite de RAM
pour le processus entier. Une GUI bloquee ne cree pas une liste infinie d'images.

Arret : detacher le worker du callback reseau, l'arreter et attendre sa fin,
puis detruire la WebSocket. Aucun callback GUI n'est requis pour cette attente.

## P3 - capture Windows et conversion native

- GDI utilise un DIB top-down BGR24 reutilise. Apres GdiFlush, une copie par
  ligne retire seulement le padding DWORD, sans boucle Pascal BGRA -> RGB.
- `TRgbFrame.Order` indique explicitement RGB ou BGR. Redimensionnement,
  comparaison des regions, cache et encodeur conservent cet ordre.
- TurboJPEG recoit TJPF_BGR sur GDI ; le JPEG reste 4:4:4, meme qualite et
  meme limite 512x512. Ce changement de disposition memoire ne change pas les
  canaux visibles. Le pont H.264 RGB uniquement convertit a sa propre frontiere.
- Le convertisseur C partage par DXGI/portail/SCK a un chemin natif sans
  divisions par pixel lorsque l'image n'est ni tournee ni redimensionnee.
  Les autres geometries conservent le chemin valide generique.

DXGI reste optionnel (`--with-dxgi` au build, `--backend dxgi --monitor 1`
a l'execution). Aucun changement silencieux vers ce backend. Le code de
conversion a ete teste ici ; le pont D3D11 et ses performances restent a tester
sur Windows. GDI BGR24 n'est pas annonce plus rapide sur tous les pilotes.

## Construction Windows x86 - commande habituelle conservee

Recompiler LES DEUX executables : la structure interne de pixels a change.
Ne pas reutiliser des .ppu de la version precedente. Le script utilise -B.

```bat
cd /d C:\tranquilit\kvmlazarus
build_standalone_windows.cmd --arch x86 ^
  --fpc "C:\lazarus_4_8\fpc\bin\i386-win32\fpc.exe" ^
  --lazbuild "C:\lazarus_4_8\lazarus\lazbuild.exe" ^
  --toolchain-bin "C:\msys64\mingw32\bin" ^
  --turbojpeg-archive "C:\msys64\mingw32\lib\libturbojpeg.a" ^
  --mormot-dir "C:\tranquilit\mORMot2"
```

Les scripts build_standalone.py/.cmd sont inchanges par cette passe.
Pas de modification de mORMot2 ; pas de nouvelle DLL privee. Les nouvelles
unites Pascal sont liees normalement. La variante x64 garde les options et
outils x64 deja utilises. Les projets Standalone doivent etre regeneres depuis
les .lpi mis a jour, pas recouverts d'une ancienne copie generee.

## Tests Pascal a executer apres preparation du profil autonome

```bat
"C:\Program Files\Python314\python.exe" tests\run_p123_tests.py ^
  --arch x86 --standalone ^
  --fpc "C:\lazarus_4_8\fpc\bin\i386-win32\fpc.exe" ^
  --toolchain-bin "C:\msys64\mingw32\bin"
```

Ce runner compile et execute le vrai code Pascal, pas une simulation Python :
BGR/padding, propagation de format, copie sur ecriture, delais, flow existant,
worker TurboJPEG et repli FCL, ACK sans interrogation GUI, 50 presentations
non consommees, NACK, resynchronisation, D/I ordonnes, pause, changement de
resolution/generation, arrets repetes, limites et presentation GDI hors ecran.

Ajouter `--bench-windows` pour mesurer les appels de capture sur un moniteur
interactif avec le programme `bench_p123_capture_win.lpr`. Il imprime GDI puis
DXGI si disponible. Ce n'est pas un test de FPS reseau et DXGI peut retourner
une image inchangee. Si DXGI n'est pas integre, il l'annonce NOT RUN.

Sous Linux, `python3 tests/run_p123_tests.py` utilise FPC et TurboJPEG systeme ;
ajouter `--standalone` apres preparation des archives du profil Linux.

## Recette de performance sans changer les criteres de qualite

Commencer avec GDI, un seul moniteur, memes dimensions/qualite/FPS avant/apres.
Exemple local (ne pas utiliser ce jeton d'exemple en production) :

```bat
set "MESH_KVM_TOKEN=remplacer-par-un-secret-long-aleatoire"
dist\i386-win32\MeshKVMServer.exe --listen 127.0.0.1 --port 7900 ^
  --control --backend gdi --monitor 1 --encoder turbojpeg ^
  --fps 20 --quality 90 --max-width 3840 --max-height 2160 --no-adaptive ^
  --metrics-csv perf_p123.csv
```

`perf_p123.csv` ne doit pas deja exister. Pour un autre PC, conserver les
parametres reseau/TLS deja utilises, sans desactiver la securite pour le test.
Tester 30-60 s avec le meme mouvement de fenetre. Relever le CSV serveur et le
journal client, chemin dans le statut F8 ou via MESHKVM_CLIENT_LOG.

Nouveaux compteurs client (intervalle ~5 s) : decode worker ms, copie CPU ms,
commit+ACK ms, import LCL ms, PaintBox ms, PaintBox/s, presentations,
presentations fusionnees, file max octets, TurboJPEG/FCL, NACK. ACK/s compte les
ACK generes par le client, pas une mesure du rafraichissement physique. PaintBox/s
compte les appels de peinture, pas necessairement des images distinctes.
L'ACK serveur mesure maintenant le reseau et la composition CPU, pas la peinture.

## Limites assumees

P4 n'est pas dans cette livraison : pas de nouveaux defauts LAN, pas de mode
1:1 avec defilement. Le serveur garde ses valeurs par defaut (3 FPS/65/1080p,
adaptatif) ; les options explicites ci-dessus sont importantes. La vue ajuste
encore l'image a la fenetre. Cette passe ne rend pas sans perte le JPEG et ne
corrige pas a elle seule une reduction de resolution configuree.

Sources d'API consultees : documentation officielle Microsoft StretchDIBits /
CreateDIBSection / GdiFlush, FPC TThread/WaitFor, documentation Lazarus RawImage
et en-tete officiel libjpeg-turbo. Il ne s'agit pas d'un port ligne a ligne du
moteur MeshAgent ni d'une equivalence de performances mesuree.

La livraison source exclut la .so Linux precompilee et les deux .lps de la
copie utilisateur. Ils ne sont pas necessaires au build autonome.
